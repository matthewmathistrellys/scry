# Claude Code runtime: sessions, cache, compaction, hooks

**What this is.** Working knowledge about how Claude Code itself behaves, kept
because every hook Scry ships is built on it. Every claim is pinned to the
version and date it was read and says where it came from. Claude Code changes
weekly; a claim here is a dated reading, not current truth. Re-verify against
the binary or the docs before building on one that matters.

**How to read the source tags.** `docs` = the page at code.claude.com/docs,
read on the date shown. `binary` = a string found in the installed Claude
Code binary (`~/.local/share/claude/versions/<v>`). `run` = observed by
running it on this machine. `inferred` = follows from the above but was not
itself observed.

Started 2026-09-10 against Claude Code 2.1.268 (Matt: "build some knowledge
here so we know what we're doing").

---

## 1. The prompt cache and its TTL

- **What is cached.** Each request re-sends the whole context. The API caches
  by exact prefix match. Layers, in order: system prompt (tools) → project
  context (CLAUDE.md, memory, rules) → conversation. A change high in the
  prefix invalidates everything after it. (docs, prompt-caching, 2026-09-10)
- **TTL.** Two lifetimes exist: 5 minutes and 1 hour. Every request that hits
  the cache resets the timer. Main conversation on a Claude subscription,
  within plan usage: **1 hour**. Once the session is drawing on usage credits,
  or on an API key / Bedrock / Vertex / Foundry: **5 minutes**. Everything
  outside the main conversation (subagents, workflows, compaction, session
  titles) gets 5 minutes by default. (docs, prompt-caching "Which TTL each
  request gets", 2026-09-10; the same rule is in the binary's settings help
  text, 2.1.268)
- **Choosing it.** `CLAUDE_CODE_PROMPT_CACHE_TTL` / `promptCacheTtl` for the
  main conversation; `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL` /
  `subagentPromptCacheTtl` for the rest; `FORCE_PROMPT_CACHING_5M=1` forces 5m
  everywhere; `ENABLE_PROMPT_CACHING_1H=1` requests 1h everywhere. Order of
  precedence is force-5m → env → setting → subagent frontmatter → enable-1h →
  bucket default. Requires ≥ 2.1.242. (docs, 2026-09-10; env names also
  present in the 2.1.268 binary)
- **Cost when it expires.** The first request after a gap longer than the TTL
  reprocesses the full context as uncached input, then writes a new cache.
  There is no partial recovery. (docs, costs "Why usage climbs", 2026-09-10)
- **Where Claude Code reports it.** Only the status-line payload, object
  `prompt_cache`: `warm`, `ttl`, `expires_at` (epoch seconds), `requests`,
  `misses`, `expected_rebuilds`, `hit_ratio`, `cache_write_tokens`,
  `last_miss_at`, `last_miss_cause`, and `recache_tokens_if_cold` — the
  tokens the next request re-reads if the cache has gone cold by then. No
  hook event carries any of this. (docs, statusline "Prompt cache fields",
  2026-09-10; `expires_at` confirmed in the 2.1.267 binary per Scry's
  cache_deadline_statusline.sh)
- **The status line re-runs itself when a warm cache reaches `expires_at`**,
  plus on each assistant message, after `/compact`, on permission-mode
  change, and on a `refreshInterval` timer if set. It does NOT tick on its
  own otherwise, so a minutes-left figure goes stale between events.
  (docs, statusline "How status lines work", 2026-09-10)

## 2. Compaction

- **What it is.** One extra request with the same system prompt, tools and
  history as the conversation plus a summarization instruction as a final
  user message. The history is then replaced by the summary. The prompt
  begins "Your task is to create a detailed summary of the conversation so
  far…" and asks for `<summary>` tags. (docs, prompt-caching "Compacting the
  conversation", 2026-09-10; prompt text in the 2.1.268 binary)
- **Which model.** The session's model. No compaction-model setting was found
  in the 2.1.268 binary (searched for `compactionModel`,
  `CLAUDE_CODE_COMPACT*`); session *titles* are the thing generated by a
  Haiku-class model, not compaction. (binary search 2026-09-10 — absence of
  evidence, so `inferred`; docs sessions page for the title model)
- **What it costs, warm.** Reads the prefix from cache, so a mid-session
  `/compact` costs a fraction of the context size and most of the time is
  spent generating the summary. (docs, 2026-09-10)
- **What it costs, cold.** After a gap longer than the TTL there is no cache
  to read, so the summarization request reprocesses the full history as
  uncached input. "This is why /compact costs the most when you resume an
  old session." (docs, verbatim, 2026-09-10)
- **The catch-22, resolved.** Once the cache is cold, *every* path pays one
  full re-read: compacting, continuing as-is, or resuming from a summary
  ("the next request processes the full history once no matter which of the
  dialog's options you pick" — docs, sessions "Resume from a summary").
  Compacting cold is still the better of those because every request *after*
  it carries the short summary instead of the full history. The only path
  that pays nothing is `/clear` ("`/clear` costs nothing" — docs, costs).
  So the decision is made *before* expiry, not after: while warm, write a
  handoff (cheap: reads from cache) and then either `/compact` (warm, cheap)
  or `/clear` (free) into a fresh session that starts from the handoff. That
  is the design behind Scry's cache-handoff monitor + the `/clear`
  orientation in fleet.sh. (inferred from the docs claims above)
- **Auto-compact.** Triggers as usage approaches the auto-compact window;
  `CLAUDE_CODE_AUTO_COMPACT_WINDOW` / `autoCompactWindow` override it,
  `autoCompactEnabled` turns it off. The binary also carries a
  `CLAUDE_CODE_COLD_COMPACT` flag near strings "idle_base" and "autocompact:
  tokens= level= effectiveWindow=" — its behaviour was not traced. (binary
  2.1.268, docs costs; COLD_COMPACT meaning `unknown`)
- **After compaction** the cache rebuilds for the short summary only; the
  turn after compaction is not the slow one. Project context (CLAUDE.md,
  rules) is re-read from disk at that point, so CLAUDE.md edits apply on
  `/compact`, `/clear`, or restart and never mid-session. (docs, 2026-09-10)
- **`/recap`** generates a summary for display without replacing history,
  so it keeps the cache. **`/rewind`** truncates to an already-cached prefix,
  so it is cheaper than compaction when abandoning a path. (docs, 2026-09-10)
- **Hooks.** `PreCompact` and `PostCompact` fire with `trigger: "manual" |
  "auto"`. `PreCompact` can block a compaction (the binary has "Reactive
  compact blocked by PreCompact hook"). Neither adds context. (docs hooks;
  binary 2.1.268)

## 3. `/clear`, sessions, and what survives

- **`/clear` ends the session.** It fires `SessionEnd` with `reason:
  "clear"`, then `SessionStart` for a *new* session id with `source:
  "clear"`. The old transcript stays on disk and is resumable with
  `claude --resume <id>` or `/resume`; in the same process, the rewind
  menu also has a previous-session entry. `/usage` and `cost.total_cost_usd`
  reset to zero. `/clear <name>` names the session being left. (docs
  sessions + hooks, 2026-09-10; sources `startup|resume|clear|compact|fork`
  and reasons `clear|resume|logout|prompt_input_exit|other` also present as
  matcher values in the 2.1.268 binary)
- **Why the new session knew nothing.** Scry's fleet hook reported the last
  session only when its transcript was older than the 15-minute live window;
  the session just cleared was seconds old, so it was skipped as "live".
  Fixed 2026-09-10 (scry 1.24.0): on `source: "clear"` it names the session
  left and prints its handoff. (run, this repo)
- **SessionStart stdout is context.** `SessionStart`, `UserPromptSubmit`,
  `UserPromptExpansion`, `PostModelSwitch` are the hook events whose plain
  stdout the model sees. Every other hook's stdout is not shown to the model.
  (docs hooks, 2026-09-10)
- **Resume from a summary.** On Pro/Max, resuming a session idle > ~1 hour
  and > 100k tokens opens a dialog: resume from summary (runs `/compact`
  immediately), resume as-is, or don't ask again. Any choice pays the cold
  full read once. (docs sessions, 2026-09-10)
- **Session titles** are written by a background Haiku-class request from
  the first prompt; the transcript's last `ai-title` record is the current
  title; accepting a plan or `/rename` replaces it. (docs sessions; Scry
  reads `ai-title` from the transcript tail, verified 2026-07-26)
- **Transcript path.** `~/.claude/projects/<cwd with [/._] → ->/<session
  id>.jsonl`. Format is internal and changes between versions. (docs
  sessions; encoding verified in Scry 2026-07-26)
- **What `/clear` does NOT end: the work.** A subagent, workflow agent or
  background job started before the clear keeps running. Only the
  *conversation* ends. The result then has nowhere to land: it is addressed to
  a session id that takes no more turns, and the new session is told nothing
  about it. Observed on 2026-09-11 — a session cleared mid-build, its builder
  ran on and pushed, and the replacement launched a second builder on the same
  branch (Matt; the push itself is in the PR history). Where the completion
  notification actually goes is `unknown` — not traced, and the observable
  effect is the same either way: nobody read it.
- **A subagent's owning session is recoverable from its path.**
  `~/.claude/projects/<encoded cwd>/<session id>/subagents/<subagent
  id>.jsonl` — the session-id directory that `subagents/` hangs off is the
  session that started it. That is what lets a post-`/clear` session tell its
  own orphaned agents from a stranger's. (run, verified in this repo
  2026-07-26, relied on for attribution 2026-09-11)
- **Every task leaves one file: `<task root>/<encoded cwd>/<session id>/tasks/<task
  id>.output`.** Foreground and background alike; the name is the task id.
  Two shapes. A **symlink** is a spawned agent's task and points at that
  agent's own JSONL transcript — Claude Code's own `TaskOutput` tool
  documents this verbatim and warns the file is the entire conversation. A
  **regular file** is a shell task: appended to as output is produced, with a
  trailing `[exited with code N]` once it is done. A foreground task's file is
  deleted when it completes; a background one's is kept. (run + tool schema,
  2026-09-11)
- **Correction, same day.** An earlier note here claimed the file is "created
  empty, does not grow while it runs, and is written in one go at exit", so
  that a zero-byte file meant an unfinished job. That was a bad
  generalisation from a single probe whose command printed nothing until its
  last line. Re-observed: a foreground command's file sat at 8 bytes
  mid-command and vanished on completion. **Empty means "has printed
  nothing yet", not "has not finished"** — the exit marker is the finished
  test, not the size. Worth keeping as a reminder that one observation of a
  file is an observation of one command's output habits.
- **`outputDir` is memoized per process, not per session.** `qt()` in the
  bundle resolves `<task root>/<encoded cwd>/<session id>/tasks` once and
  caches it on a module-level singleton, so it does not follow a later
  session-id change. (binary, 2026-09-11, minified — read as a strong hint,
  not a traced behaviour)
- **`repointTaskOutputSymlinks` exists, but for cwd changes.** It runs inside
  `relocateSessionTranscript`, which moves `<projects>/<encoded cwd>/<session
  id>/` when a session changes directory — the session id is identical on
  both sides. So it is evidence that the runtime works to keep live task
  output resolvable when files move, and NOT evidence about `/clear`. Noted
  because it reads like the latter at first glance. (binary, 2026-09-11)
- **Cache scope.** Effectively one machine + one directory: the prefix
  carries cwd, platform, shell, OS version and the git snapshot at start.
  Worktrees of the same repo have different caches. Parallel sessions in the
  same directory share one. (docs prompt-caching "Cache scope", 2026-09-10)

## 4. Other cache-relevant facts worth remembering

- Model switch, effort change (except Fable 5.1 on subscription/API key),
  fast mode on, non-deferred MCP server connect/disconnect, bare tool deny
  rule, Claude Code upgrade: each invalidates the whole cache. (docs)
- Editing CLAUDE.md, changing permission mode, invoking skills, spawning
  subagents, `/recap`, `/rewind`: keep it. (docs)
- Subagents get their own cache with a 5-minute TTL by default; forks share
  the parent's prefix. Workflow fan-outs hold same-prefix agents up to 5s so
  the first one's cache write serves the rest. (docs)
- Cross-session messages, scheduled tasks, `/loop`, and goal check-ins each
  send the full context while the session sits idle — they keep the cache
  warm, and they cost a request each time. (docs costs, 2026-09-10)

## 5. Open questions

- What `CLAUDE_CODE_ENABLE_AWAY_SUMMARY` does (binary flag, untraced; the
  name suggests a summary generated while away — if it exists it is the
  feature this whole line of work wants).
- Whether the status-line `refreshInterval` timer keeps firing while the
  terminal is unfocused for hours (not tested).
- Whether `$TMPDIR/claude-<uid>/.../tasks/` is stock Claude Code or specific
  to the remote/container runtime it was observed on. It was read on a Linux
  container where `TMPDIR` was unset; macOS sets `TMPDIR` per user, so the
  root would differ. `fleet.sh` therefore treats an absent directory as
  silence rather than as "nothing running" — if the layout is wrong or absent
  the fifth fact simply loses its background-job half, and the subagent half,
  which is verified, still speaks.
- Where a background job's completion notification goes when its session was
  cleared before it finished (see §3).
